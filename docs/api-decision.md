## 1. 쓰는 API

| 용도 | API | 호출 | 비고 |
|------|-----|------|------|
| 영상 강의 | YouTube Data API v3 | `search.list`(type=playlist, **channelId=허용 채널**) + `playlists.list`(강의 수) + `search.list`(type=video, **videoDuration=long**, channelId=허용 채널) + `videos.list`(길이·조회수) | 후보 찾기 1번 = **약 202 units** (검색 2×100 + 상세 2×1). 기본 할당량 하루 10,000 units **[확인 필요: 프로젝트 콘솔의 실제 할당량]** |
| 책 | 카카오 책 검색 | `GET /v3/search/book?target=title&size=10&query=EBS <과목> <단원>` (없으면 `EBS <과목>`) | 허용 출판사(EBS)만 남김 |

- 학생 화면에서는 **어느 바깥 API도 부르지 않습니다** (할당량 0). 바깥 API는 내부 확인 페이지의 "후보 찾기"를 누를 때만 부릅니다.
- **제외: 알라딘 Open API.** 2026-11-01 서비스 종료.
- **EBSi 사이트**는 공개 API가 없어(PRD 11장) 크롤링하지 않고, 추천 화면에 **"EBSi에서 이 과목 강좌 찾기" 링크만** 둡니다 (중학생은 EBS 중학). 과목별 깊은 링크 주소는 확인하지 못해 첫 화면으로 연결 **[확인 필요]**.

## 2. 구조

```
[내부 확인 페이지 /admin/review.html]   ← 학생 화면과 연결 안 됨
  ├─ "이 단원 후보 찾기" → POST /api/collect {grade, courseId, unit}
  │     서버: 허용 채널에서 재생목록·20분 넘는 영상, EBS 교재 검색 → 거르기 → 추천순 점수
  │           → data/recommendations.json 에 candidate 로 저장
  └─ 후보마다 [승인] [제외] (처리한 항목은 [후보로 되돌리기]) → POST /api/review
        [승인] 한 번이면 approved. 추천 이유는 서버가 자동으로 만듦 ("이유 고치기"는 접힌 선택 기능)

[학생 추천 화면]
  └─ GET /api/recs?course=<코스>&unit=<단원>&school=high   ← 승인(approved)된 것만, 영상 2·책 2, 추천순
  └─ <img src="/api/img?u=…">                               ← 표지·썸네일은 서버를 거쳐 받음
```

**승인 흐름 (PRD Q-3): 후보 찾기 → 사용자 [승인] 한 번** (리뷰어 확인 단계·추천 이유 입력 생략, 사용자 결정 2026-11-11, `qitem-20261111122312-030daeec2ebe58c9`)

| 상태 `review.status` | 누가 | 학생 화면 |
|------|------|------|
| `candidate` | 후보 찾기 | 안 보임 → "준비 중" |
| `approved` | **사용자 [승인]** (추천 이유 자동 생성, 승인일 기록) | **보임** |
| `retired` | 사용자 [제외] (상업 홍보, 학년 안 맞음, 링크 깨짐 등) | 안 보임 |

- **추천 이유 자동 생성 (F-4.4):** 사실만 짧게 이어 붙임. 영상: `<단원> 단원 · <채널> 무료 강의 · <n>분` (재생목록이면 `<n>강 재생목록`), 책: 항상 `<과목> 과목 · EBS 교재` (책은 과목 단위로 여러 단원에 나오므로 단원 이름을 쓰지 않음).
  - **범위:** 자동 이유는 "무엇인지"(단원·출처·길이)만 말하는 **사실 요약**입니다. PRD F-4.4가 말하는 "왜 이 학생 수준에 맞는지·난이도"와의 연결은 넣지 않았고, **1-B에서** 추천 방향표(개념/유형/심화)·난이도와 함께 다룹니다 (사용자의 승인 단순화 결정에 따른 차이를 기록). 예: "삼각함수 단원 · EBSi 무료 강의 · 59분". 평가·광고 문구(최고, 강추 등)는 넣지 않음 (`npm test`로 확인). 이유가 이미 있으면 그대로 둠.
- **사용자가 승인하는 방법:** `npm run dev` → `http://localhost:3000/admin/review.html` → 학년·과목·단원을 고르고 → 후보 영상·책을 열어 본 뒤 **[승인]** 또는 **[제외]**. 이유를 바꾸고 싶을 때만 "이유 고치기(선택)"를 펼침. 또는 `data/recommendations.json`에서 `review.status`를 직접 바꿔도 됩니다.
- 서버는 `candidate`·`approved`·`retired`만 받고, id·상태가 문자열이 아니거나 JSON이 깨졌으면 400. 거절할 때는 파일을 쓰지 않음.
- 학생 응답에는 검토 상태·점수·조회수 같은 내부 필드를 넣지 않습니다.

## 3. 키 관리

| 규칙 | 내용 |
|------|------|
| 위치 | 프로젝트 루트 `.env.local`: `KAKAO_REST_API_KEY`, `YOUTUBE_API_KEY` (사용자가 넣음) |
| git | `.gitignore`의 `.env.*`로 제외됨 (`git check-ignore` 확인) |
| 코드·문서 | 키 값은 어디에도 쓰지 않음. `bs-config.cjs`에도 키나 PC 경로 없음 (상대 경로만) |
| 로그 | 서버는 키를 출력하지 않음. 바깥 API 오류 본문은 넘기지 않음 |
| 키를 바꿀 때 | `.env.local`만 고치면 됨. 요청 때마다 읽으므로 서버 재시작 필요 없음 |

**배포할 때 할 일 (1-B 이후):**
- YouTube 키: Google Cloud 콘솔에서 **API 제한(YouTube Data API v3만)** + **애플리케이션 제한(서버 IP)**.
- 카카오 키: 카카오 개발자 콘솔에서 **허용 IP**(서버 IP) 지정.
- 키는 배포 환경 변수로 넣고, 서버에서만 부릅니다 (Next.js에서는 Route Handler). 개발용·운영용 키를 나눕니다.
- **내부 확인 페이지(`design/admin/review.html`)는 로그인 없는 로컬 전용입니다. 실제 배포(1-C)에서는 배포물에서 빼거나, 관리자 로그인 뒤에만 열리게 막아야 합니다.** `/api/collect`, `/api/review`도 같습니다 (지금은 이 컴퓨터의 미리보기 서버에서만 열리고 Origin 검사만 함).

## 5. 추천순 기준

후보 찾기 때 점수를 매겨 저장하고, 학생 화면은 이 순서로 보여 줍니다 (`server/api.cjs` `rankScore`, `sortRecs`).

1. **사람이 정한 순서** (`rank`, 있으면 최우선)
2. **무료 먼저** (F-4.5: EBS 영상은 무료, 책은 유료)
3. 점수가 높은 순:
   - 단원 이름이 제목에 있음 **+3**, 과목 이름이 제목에 있음 **+2**
   - **강좌 재생목록 +2** (강의 5개 이상이면 +1 더)
   - 20분 이상 영상 **+1**
   - 조회수 보조 0~1 (log), 책은 최근 출간 0~1

- 영역마다 **영상 강의 최대 3개, 책 최대 2권** — **사용자 결정 2026-11-12: 영역당 강의 최대 3개** (`qitem-20261111153530-b068df904fbd0780`, 같은 날의 "5개" 결정을 대체). README·PRD F-4.3의 "강의 1~2개"와 다르며, README·PRD는 수정 금지라 여기에 기록. 숫자는 `data/sources.json`의 `display.maxVideosPerArea`·`maxBooksPerArea`. 책은 과목 단위라 영역마다 같은 책이 반복되므로 2권을 유지.
- **단원 강의가 없을 때의 대체 표시:** ① 그 단원 강의 → ② 과목 전체(`unit: "*"`) 강의로 채움 → ③ 그래도 없으면 같은 과목의 다른 단원 강의를 "이 단원만 다루는 강의를 준비하는 동안, 같은 과목의 강의를 보여 줘요." 안내와 함께 (`/api/recs`의 `videosScope: 'course'`) → ④ 그것도 없을 때만 "준비 중" + EBSi 링크.
- **후보 찾기 방식 (2026-11-12, EBS 조사 추천 1·2 적용):**
  - 재생목록은 단원마다 `search`(100 units)를 쓰지 않고, 채널 재생목록 전체를 `playlists.list`(50개당 1 unit, 하루 캐시)로 받아 **제목으로 맞춤**. 과목 이름 + `curriculum.json`의 `searchAlias`(예: 대수 → "수학Ⅰ", 미적분Ⅰ → "수학Ⅱ"), `searchExclude`(예: "공통수학"이 "수학Ⅰ"에 걸리지 않게)를 씀. 로마 숫자 Ⅰ·Ⅱ와 띄어쓰기는 같게 취급. 강의 2개 이상인 재생목록만. 단원 이름까지 제목에 있으면 그 단원, 아니면 과목 전체(`*`)로 저장.
  - 영상은 단원마다 `search`(20분 넘는 영상) 1번 + 상세 1번.
  - **비용: 단원당 약 101 units** (전에는 202) + 채널 재생목록 목록 하루 1번. 진행표: `docs/recommendation-progress.md`.
- **책은 과목 단위:** 카카오 결과가 단원보다 과목 이름(예: "올림포스 대수")으로 나오므로, 새 책 후보는 `unit: "*"`(과목 전체)로 한 번만 저장하고, 학생 화면은 단원 결과에 그 과목의 승인된 책을 함께 보여 줌 (같은 책은 한 번만). 처음 돌린 9권도 2026-11-11 과목 단위(`unit: "*"`, id `m22-alg|*|book:…`)로 옮김 (`npm test`가 책은 `*`인지, id 규칙·중복을 검사).
- **다시 찾기:** 승인했거나 제외한 항목은 후보 찾기를 다시 돌려도 덮어쓰지 않음.
- 파일 쓰기가 한 번 실패해도(예: 백신이 파일을 잡음) 그 요청만 실패하고 다음 쓰기는 이어짐.
- 처음 실제로 해 본 결과(고2 대수·삼각함수, 2026-11-11): EBSi 50분 넘는 강의 5개, EBS 교재 9권이 후보로 들어옴. **재생목록은 0개** — 재생목록이 걸러진 것인지 이 검색어에 맞는 공개 재생목록이 없는 것인지 아직 확인하지 않음 [확인 필요].

## 7. 개인정보·이미지

- 학생 화면이 서버로 보내는 것: 과목(코스) id, 단원 이름, 중/고. **성적·체크 결과는 보내지 않습니다.** 바깥 API로는 아무것도 보내지 않습니다.
- **이미지 서버 경유 (`/api/img?u=`)**: 학생 브라우저가 kakaocdn·ytimg에 직접 접속하지 않아 학생 IP가 그쪽에 가지 않습니다.
  - **열린 프록시 금지:** `https`만, 허용 도메인 `i.ytimg.com`, `search1.kakaocdn.net`만(정확히 일치), 포트·사용자 정보가 붙은 주소 거절, 넘겨주기(redirect) 따라가지 않음. **그리고 `data/recommendations.json`에 저장된 항목의 썸네일 주소와 정확히 같을 때만** 중계 (카카오 썸네일 서버는 `fname=<아무 주소>`를 대신 받아 오므로 호스트 검사만으로는 부족 — 리뷰 반영).
  - 이미지 형식(jpeg/png/webp/gif)만, **512KB 이하**(알려 준 길이를 먼저 보고, 받는 도중에도 넘으면 끊음), 메모리 캐시 300개, 브라우저 캐시 하루.
- 후보 찾기 검색어: 학년·과목·단원 이름만 (예: `대수 삼각함수`, `중2 수학 일차함수`).

## 8. 보안 (이 컴퓨터의 미리보기 서버)

- `/api/collect`, `/api/review`는 **POST + `Content-Type: application/json` + Origin이 `http://localhost:3000`(또는 127.0.0.1)** 일 때만 받습니다. 다른 웹사이트가 이 컴퓨터의 미리보기 서버로 요청을 보내 할당량을 쓰거나 파일을 바꾸지 못하게 합니다 (바깥 API를 부르기 전에 403).
- 요청 본문 10KB 제한, 파일 쓰기는 한 번에 하나씩·임시 파일 후 이름 바꾸기.
- 확인: `npm test` (모의 응답으로 거르기·추천순·승인 규칙·이미지 주소 검사, 서버가 켜져 있으면 403/400/405 응답과 키 흔적 없음 확인. 바깥 API는 부르지 않음).
