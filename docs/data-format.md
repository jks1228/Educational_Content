> 이 문서는 앱(1-B)이 그대로 읽을 데이터의 모양을 정합니다. 실제 추천 목록 채우기(0단계 ④)는 이번 범위가 아닙니다.
> 예시 파일의 추천 항목은 **가상 데이터**입니다. 실제 강의·책이 아니며, 링크는 `example.com`입니다.

## 1. 파일 구성

| 파일 (1-B 기준 위치 제안) | 내용 | 바뀌는 때 |
|---------------------------|------|-----------|
| `data/curriculum.json` (**만듦**, 3-1절) | 학년 → 과목 → 과목(코스) → 단원. 프로토타입이 지금 이 파일을 읽음 | 교육과정 적용 학년이 바뀔 때 (R-3) |
| `data/areas.json` | (예전 안) 학년·과목별 진단 영역 목록 → `curriculum.json`으로 대체 | |
| `data/rules.json` | 성적 → 수준 기준표, 학년별 등급제, 추천 방향표 | 학년도가 바뀔 때, 경계값을 조정할 때 (Q-2) |
| `data/items.json` | 강의·책 추천 항목 | 0단계 ④, 정기 점검 (R-2) |

세 파일 모두 맨 위에 `schemaVersion`(형식 버전)과 `schoolYear`(기준 학년도)를 둡니다. 학년도가 바뀌면 규칙을 새로 점검해야 하기 때문입니다 (R-3).

## 3-1. 과목·단원 (`curriculum.json`, v2, 2026-11-11)

사용자 피드백(2026-11-11): "고등학생은 미적분도 있고 통계도 여러 과목이 많은데 선택지가 빈약하다, 저학년 느낌". 그래서 영역을 **학년 → 과목(국·영·수) → 과목(코스) → 단원**으로 넓혔습니다. 고등학교는 학교마다 편성이 달라서, 학생이 **지금 배우는 과목(코스)을 고르고** 그 단원으로 체크합니다.

| 필드 | 설명 |
|------|------|
| `curriculumByGrade` | 2026학년도 학년별 교육과정 (중1·중2·고1·고2 = 2022, 중3·고3 = 2015) |
| `groups[]` | 과목 묶음: `term`(중학교 배운 범위: 1학기·2학기), `common`(공통), `general`(일반 선택), `exam`(수능 대비), `career`(진로 선택), `fusion`(융합 선택), `all`(하나뿐). `collapsed: true`인 묶음은 1단계에서 접어 둠 |
| `courses[].id` | 코스 이름 (예: `m22-alg` = 2022 대수) |
| `courses[].subject` / `curriculum` / `group` / `label` | 과목, 교육과정, 묶음, 화면 이름 |
| `courses[].search` | (선택) 검색어에 쓸 이름. 없으면 `label` (예: "공통국어1·2" → "공통국어") |
| `courses[].units[]` | 단원(대단원) 이름. **비어 있으면** 화면에서 "(과목) 전체" 한 칸으로 체크 |
| `courses[].source` | `sources`의 키. `official`(교육부 고시 원문), `secondary`(시판 교재 목차, 보조), `unverified`(대조 못 함) |
| `courses[].verify` | `true` = **[확인 필요]**: 교육부 고시 원문과 단원까지 대조하지 못함 |
| `offer[학년][과목]` | 그 학년에서 고를 수 있는 코스 id 목록. 하나뿐이면 고르는 칸 없이 바로 사용 |

- **단원 id**는 앱이 만듭니다: `<학년>-<과목>-<코스 id>-<단원 번호>` (예: `h2-math-m22-alg-2` = 고2 대수 삼각함수). README 파일 이름 규칙(`<학년>-<과목>-<영역 영문>`)과 다르므로, 1-B에서 추천 항목의 `areaIds`도 이 형식을 씁니다.
- 교재 상품명·출판사명은 넣지 않습니다(광고 배제). 시판 교재 목차는 단원 이름 대조용 보조 자료로만 썼습니다.
- 확인은 `npm test` (`tests/prototype.test.mjs`): 형식, `offer`가 가리키는 코스가 실제로 있는지, 고등 수학 선택지, 상품명 없음, `verify=false`는 공식 출처인지.

## 4. 규칙 (`rules.json`)
README 표를 그대로 옮깁니다. 앱 코드에 숫자를 직접 쓰지 않고 이 파일에서 읽습니다 (R-3).

| 필드 | 내용 |
|------|------|
| `levelIsProvisional` | `true` = 경계값이 임시 기준. 화면에 "임시 기준" 안내 표시 (F-3.4) |
| `naesinScaleByGrade` | 학년별 내신 등급제. 2026학년도: `h1`·`h2` = 5등급제, `h3` = 9등급제 (F-1.5) |
| `levelThresholds` | 입력 방식별 상·중·하 경계 (README "성적 수준 정하기" 표)<br>`middleScore`(점수), `middleAchievement`(A~E), `middleAchievement3`(체육·예술 A~C, MVP 이후용), `naesin9`, `naesin5`, `mock9`(모의고사) |
| `purposeRule` | 성적을 둘 다 입력했을 때 기준 (F-3.2): `naesin`→내신, `suneung`→모의고사, `both`→두 수준 중 낮은 쪽. 하나만 입력하면 그 성적 |
| `directions` | 추천 방향표 6칸 (README "추천 방향 고르기"). 칸마다 `lectureType`, `bookType`, 화면 문구 `label` |
| `allConfidentRule` | 한 과목 모든 영역이 "자신 있음"이면 자기 수준의 `normal` 칸을 사용 (F-4.2) |
| `maxPerArea` | 영역당 강의 최대 2, 책 최대 2 (F-4.3) |

## 5. 추천 항목 (`items.json`)
PRD F-5.1의 필수 필드에 **검토 상태** 필드를 더했습니다. Q-3(추천 데이터를 누가 고르고 검토하나)에 대해 사용자가 정한 흐름 "리드 후보 작성 → 리뷰어 근거·링크 확인 → 사용자 승인분만 반영"을 담기 위해서입니다.

> **바뀜 (사용자 결정 2026-11-11, `qitem-20261111122312-030daeec2ebe58c9`): Q-3 승인 흐름은 "후보 찾기 → 사용자 [승인] 한 번"입니다.** 리뷰어 확인 단계(`reviewed`)와 추천 이유 입력은 뺐습니다. 추천 이유는 승인할 때 **자동으로 만들고**(예: "삼각함수 단원 · EBSi 무료 강의 · 59분", "대수 과목 · EBS 교재"), 내부 확인 페이지의 "이유 고치기(선택)"로만 고칩니다. 자동 이유는 **사실 요약**이고, 학생 수준·난이도와의 연결(F-4.4)은 1-B에서 다룹니다. 지금 프로토타입의 실제 저장 파일은 `data/recommendations.json`이고 필드는 `docs/api-decision.md` 2절을 따릅니다.

## 6. 앱이 지킬 규칙 (1-B 구현 기준)
1. **화면에는 `review.status = approved`이고 필수 필드가 모두 있는 항목만** 나옵니다. 필수 필드가 빠진 항목은 숨기고 점검 목록에 올립니다 (F-5.3).
2. 추천 고르기: (학년, 과목, 영역, 추천 방향표 칸의 `lectureType`/`bookType`)이 맞는 항목 → 강의는 `isFree` 먼저, 그다음 `rank` → 강의·책 각각 최대 2개. **→ 바뀜 (사용자 결정 2026-11-12): 영역당 강의 최대 3개(같은 날 "5개"를 대체), 책 최대 2권. 단원 강의가 없으면 같은 과목 강의로 대체 표시** (`data/sources.json` `display`, docs/api-decision.md 5절).
3. 맞는 항목이 없으면 "준비 중" 안내를 보여 줍니다 (F-4.7).
4. **한 과목의 모든 영역이 "자신 있음"일 때** (F-4.2): 영역별 추천 대신, 과목 전체에 자기 수준의 `normal` 칸 추천을 **한 묶음**(강의 1~2, 책 1~2) 보여 줍니다. 고르는 조건은 (학년, 과목, `type`)만 보고 영역은 따지지 않습니다.
5. `difficulty`는 화면 표시용이고, 고르는 조건에는 쓰지 않습니다 (고르기는 추천 방향표의 `type`이 결정).
6. `curriculum`은 고르는 조건에 쓰지 않지만, **데이터 점검 단계에서** 항목의 `curriculum`이 연결된 영역의 `curriculum`과 다르면 경고합니다.
7. 중학생 점수는 **0~100 정수**만 받습니다. 그래서 `middleScore` 표(0~69 / 70~89 / 90~100)에 빈틈이 없습니다. 등급도 정수만 받습니다.
8. 성적, 영역 체크 결과는 **이 데이터 파일에 저장하지 않습니다.** 모두 브라우저 안에서만 계산합니다 (NF-3).

## 7. 예시 데이터로 따라가 보기 (대표 사용 상황 3)
고3, 내신 2등급(9등급제) + 모의고사 4등급, 학습 목적 "둘 다", 영어 "독해" 약함
1. `naesinScaleByGrade.h3 = 9` → `naesin9`: 2등급 = `high`
2. `mock9`: 4등급 = `mid`

4. `directions` 중 `mid` + `weak` → `concept-review` + `type-workbook` ("개념 정리 강의 + 유형별 문제집")
5. `items`에서 `areaIds`에 `h3-english-reading`이 있고 `type`이 맞는 항목을 고름 → 예시 파일의 가상 항목 2건 (단, 예시는 `candidate` 상태라 실제 앱에서는 안 보임)
